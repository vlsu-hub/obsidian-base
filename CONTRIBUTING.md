# Регламент ведения репозитория и контрибьютинга

Добро пожаловать в регламент совместной работы над нашей базой знаний! Данный документ является **строгим техническим стандартом**. Наша цель — поддерживать репозиторий в идеальном порядке, где каждый конспект легко найти, приятно читать (как в Obsidian, так и на GitHub) и в котором нет "битых" ссылок или сломанной верстки.

---

> [!IMPORTANT]
> **Автоматическая проверка (CI/CD Бот)**
>
> Наш репозиторий защищен автоматическим Python-скриптом (ботом). Бот запускается каждый раз, когда вы создаете **Pull Request (PR)**. 
> 
> * Бот анализирует список файлов через `changed_files.txt`. Это значит, что он проверяет **только те файлы, которые вы изменили или добавили**. Вас не заблокируют за чужие старые ошибки.
> * Проверка выполняется с помощью жестких регулярных выражений (RegEx) и парсеров.
> * Если скрипт находит хотя бы одну ошибку (превышен размер, неверное имя файла, забытый тег), он прерывает работу с кодом `sys.exit(1)`, и ваш PR получает красный крестик ❌. Слияние с основной базой блокируется.
> * **Защищенные файлы:** Любое изменение системных файлов `.gitignore` или `contributing.md` вызовет системное предупреждение `::warning::` в логах CI/CD. Делайте это только по согласованию с администраторами базы.

## ЧАСТЬ 1. Git Workflow и отправка конспектов

В проекте участвуют не только программисты, поэтому мы настоятельно рекомендуем использовать визуальный клиент **GitHub Desktop**. Это минимизирует шанс случайно затереть чужую работу или запутаться в ветках.

### Терминология

* **Upstream (Главный репозиторий):** Общая база знаний группы/курса. Писать напрямую туда нельзя.
* **Origin (Ваш Форк):** Ваша личная копия главного репозитория в вашем аккаунте GitHub. Вы работаете в ней.

---

### 1.1. Основной алгоритм (GitHub Desktop / Windows & macOS)

#### Шаг 1. Создание форка (Один раз)
Зайдите на страницу *Главного репозитория* (upstream) в браузере. В правом верхнем углу нажмите кнопку **`Fork`**. Снимите галочку "Copy the main branch only" (если она есть и вам нужны другие ветки, но обычно достаточно `main`) и создайте копию в своем аккаунте.

#### Шаг 2. Скачивание базы на ПК
Откройте программу GitHub Desktop. В верхнем меню выберите `File -> Clone repository`. Перейдите на вкладку `GitHub.com`, найдите в списке **свой форк** (он будет называться `ваш-ник/название-репо`) и нажмите `Clone`.

#### Шаг 3. Подключение Obsidian
Запустите Obsidian. Нажмите `Open folder as Vault` (Открыть папку как хранилище) и выберите папку, которую только что скачал GitHub Desktop.

#### Шаг 4. 🔴 СИНХРОНИЗАЦИЯ (Делать каждый раз перед работой!)
Пока вы спали, другие студенты могли добавить новые лекции. Если вы начнете писать без обновления, возникнет *Merge Conflict*. 

1. Откройте GitHub Desktop.
2. Вверху нажмите **`Fetch origin`**. 
3. Если в главном репозитории были изменения, программа предложит вам `Pull origin` или `Pull from upstream`. Обязательно подтвердите это, чтобы скачать свежие файлы на свой ПК.

#### Шаг 5. Работа над конспектом
Создайте файл в нужной папке (структуру см. в Части 2), заполните его и сохраните. Obsidian сохраняет файлы автоматически.

#### Шаг 6. Сохранение (Commit)
Перейдите в GitHub Desktop. Слева вы увидите список измененных вами файлов. 

В левом нижнем углу напишите название правки в поле *Summary*. Используйте понятную семантику:
* `feat: добавлен КП 03 по матану` (добавление нового)
* `fix: опечатка в ЛБ 02` (исправление)

Нажмите синюю кнопку **`Commit to main`**.

#### Шаг 7. Отправка на сервер (Push)
Нажмите кнопку **`Push origin`** в верхней панели. Теперь ваш файл находится в вашем форке на сервере GitHub.

#### Шаг 8. Создание Pull Request
Зайдите на страницу *Главного репозитория* в браузере. GitHub автоматически увидит, что в вашем форке появились новые данные, и покажет желтую плашку с кнопкой **`Compare & pull request`**. Нажмите её, оставьте комментарий (если нужно) и нажмите `Create pull request`. Бот начнет проверку!

---

### 1.2. Консольный Git (Linux / Продвинутые пользователи)

Если вы работаете через терминал, ваш воркфлоу выглядит следующим образом. 

Настройка upstream (выполняется один раз после клонирования форка):

```bash
git remote add upstream <URL_главного_репозитория>
```

Повседневная работа:

```bash
# 1. Забираем актуальные изменения из общей базы
git fetch upstream

# 2. Вливаем их в свою локальную ветку main
git checkout main
git merge upstream/main

# 3. Пишем конспект в Obsidian...

# 4. Индексируем изменения
git add .

# 5. Делаем осмысленный коммит
git commit -m "feat: добавлен КП 05 по физике"

# 6. Отправляем в СВОЙ форк (origin)
git push origin main
```

После этого переходите в браузер и создавайте Pull Request.

---

### 1.3. Что делать, если бот заблокировал PR? ❌

Если после создания Pull Request вы увидели красный крестик (Checks failed):

1. **НЕ закрывайте (Close) этот Pull Request!** Вам не нужно создавать новый.
2. Нажмите на кнопку **`Details`** рядом с упавшей проверкой.
3. В открывшемся логе консоли найдите строчки, начинающиеся с `[!] ОШИБКА ВАЛИДАЦИИ`. Бот напишет точную причину, например: `[КП 01 - Физика.md] Ошибка в теме 'Физика'. Разрешены только строчные буквы...`
4. Вернитесь в Obsidian на своем ПК и исправьте эту ошибку (переименуйте файл).
5. Откройте GitHub Desktop (или консоль), сделайте новый коммит (например, `fix: исправил имя файла для бота`) и нажмите **Push**.
6. GitHub **автоматически** подтянет этот коммит в ваш уже открытый PR, и бот запустит проверку заново!

## ЧАСТЬ 2. Файловая система, Именование и Метаданные

Строгая организация файлов необходима для корректной работы ссылок и удобной навигации внутри хранилища Obsidian. Проверяющий скрипт анализирует пути к файлам и их содержимое с помощью регулярных выражений (RegEx).

### 2.1. Структура директорий (Принцип воронки)

Файловое дерево строится по принципу жесткой вложенности. Бот проверяет пути по следующим правилам:

1. **Первый уровень (Семестры):** Папки должны содержать слово "семестр" (например, `1 семестр`, `2 семестр`).
2. **Второй уровень (Дисциплины):** Название предмета (`физика`, `математика`).
3. **Третий уровень (Тип занятий и преподаватель):** 
   * 🔴 **Обязательное условие:** Название папки должно начинаться с цифры и нижнего подчеркивания (RegEx: `^\d+_`). Это принудительно сортирует папки в интерфейсе Obsidian в нужном логическом порядке, а не по алфавиту.
   * ✅ *Правильно:* `1_лекции (Малышева ДА)`, `2_практика`.
   * ❌ *Неправильно:* `лекции Малышева`, `Лабораторные`.
4. **Папки для медиафайлов:** Любые изображения, относящиеся к семестру, обязаны находиться внутри подпапки `attachments/` (или `_attachments/`). Размещение картинок в корне предмета приведет к блокировке.
5. **Индексные файлы:** Списки лекций или оглавления всегда должны начинаться с нижнего подчеркивания (например, `_список лекций.md`). Бот игнорирует файлы, начинающиеся с `_`, при проверке префиксов имен.

---

### 2.2. Стандарт именования файлов (КРИТИЧНО)

Имена учебных markdown-файлов проверяются регулярным выражением:  
```regex
^([ПРЕФИКС]) (\d{2}) - ([a-zа-яё0-9_-]+)\.md$
```

Любое отклонение от этого формата вызывает ошибку валидации.

1. **Префикс (только заглавные буквы):**  
   Допустим строго один из четырех вариантов:
   * `КП` — Конспект / Лекция
   * `ЛБ` — Лабораторная работа
   * `ПР` — Практическое занятие / Семинар
   * `ЭКЗ` — Экзаменационный билет или материал
2. **Номер:**  
   Две цифры с ведущим нулем (`01`, `02`, `10`, `15`).
3. **Тема (после пробел-дефис-пробел):**  
   * ❌ **Запрещены:** пробелы и заглавные буквы. Пробелы в названиях файлов приводят к генерации ссылок с кодом `%20`, что часто ломает пути на разных операционных системах (Linux vs Windows).
   * ✅ **Разрешены:** строчные буквы (русские и латинские), цифры, дефисы `-` и нижние подчеркивания `_`.

> [!NOTE]
> **Примеры именования**
> 
> * ❌ `КП 01 - Законы Ньютона.md` *(ошибка: заглавные буквы и пробел)*
> * ❌ `Лекция 2 - интегралы.md` *(ошибка: неверный префикс, нет ведущего нуля)*
> * ✅ `КП 01 - законы_ньютона.md`
> * ✅ `ПР 05 - 1_й_закон_термодинамики.md`

**Кодировка:** Файлы должны быть сохранены строго в кодировке **UTF-8**. Obsidian делает это по умолчанию, однако при использовании сторонних редакторов (например, Блокнот Windows) файл может сохраниться в Windows-1251. Бот не сможет его прочитать и выдаст ошибку `UnicodeDecodeError`.

---

### 2.3. Метаданные (YAML Frontmatter)

Каждый markdown-файл обязан начинаться со служебного блока YAML. Бот извлекает этот блок и парсит его структуру. Отсутствие шапки или синтаксическая ошибка в YAML приведет к отклонению файла.

**Эталонный пример YAML-шапки:**

```yaml
---
date: 2024-09-23
tags:
  - author/user1
  - typer/user2
  - editor/user3
---
```

**Правила заполнения полей:**

* **`date`**  
  Дата фактического проведения занятия. Валидируется по стандарту ISO 8601: `YYYY-MM-DD`. Использование точек или слешей (например, `23.09.2024`) вызовет ошибку скрипта.

* **`tags` (Массив ролей)**  
  Поле должно являться YAML-массивом (списком с дефисами). Сюда записывается информация о контрибьюторах. Бот проверяет префиксы тегов и требует обязательного наличия двух ролей:
  * 🔴 `author/username` — **(Обязательно)** Автор оригинального текста (кто писал конспект на паре).
  * 🔴 `typer/username` — **(Обязательно)** Кто перенес текст в Markdown (оцифровка, набор формул). *При совпадении ролей тег дублируется с одним и тем же ником.*
  * 🟢 `editor/username` — **(Опционально)** Кто позже редактировал файл (дополнял материал, исправлял опечатки).

> [!WARNING]
> **Запрет смысловых тегов в YAML**
> 
> В блоке метаданных допускаются **только** теги ролей (`author/`, `typer/`, `editor/`). Попытка добавить предметный или статусный тег (например, `- физика` или `- #важно`) прямо в шапку приведет к ошибке: *"Недопустимый тег в YAML шапке"*.

## ЧАСТЬ 3. Style Guide: Оформление конспектов (Markdown + LaTeX)

Единообразие визуального стиля критически важно для читаемости базы знаний как в локальном приложении (Obsidian), так и в веб-интерфейсе (GitHub). Приведенные ниже правила проверяются скриптом и обязательны к исполнению.

### 3.1. Иерархия заголовков и пустые файлы

Проверяющий скрипт очищает текст от блоков кода, после чего анализирует структуру заголовков и наличие осмысленного текста.

* **Пустые файлы:** Файл не может состоять только из YAML-шапки. Бот ищет буквенно-цифровые символы (RegEx: `[a-zA-Zа-яА-Я0-9]`). Если текст конспекта отсутствует, выдается ошибка.
* **Главный заголовок (`# `):** Заголовок первого уровня используется **только один раз** в самом начале документа для обозначения темы (например, `# Законы сохранения`). Бот допускает максимум два заголовка H1 на файл, превышение этого лимита вызывает ошибку.  
  *(Примечание: заголовки, написанные внутри блоков кода, игнорируются парсером).*
* **Структура:** Для разделов применяется заголовок второго уровня (`## `), для подразделов — третьего (`### `).
* **Разделители:** Перед каждым новым крупным разделом (`## `) рекомендуется ставить горизонтальный разделитель (три дефиса `---` на пустой строке) для визуальной разгрузки текста.

---

### 3.2. Оформление формул (MathJax / LaTeX)

Для записи математических и физических выражений использование обычного текста (вида `A = F * S / t`) не допускается. Применяется синтаксис LaTeX:

* **Внутристрочные переменные:** Оборачиваются в одинарные знаки доллара `$ ... $`.  
  *Пример:* Масса $m$ умножается на скорость $\vec{v}$.
* **Блочные уравнения:** Оборачиваются в двойные знаки доллара `$$ ... $$` и располагаются по центру.
* 🔴 **Важное правило рендеринга:** Блочные формулы должны отделяться от основного текста **пустыми строками** сверху и снизу. В противном случае парсер GitHub может склеить формулу с текстом, нарушив отображение.

---

### 3.3. Блоки кода и защита от поломки верстки

В репозитории работает строгая проверка на незакрытые блоки кода (функция `has_unclosed_code_blocks`). 

* Любой блок кода, начатый тройными обратными кавычками ```` ``` ```` или тильдами ```` ~~~ ````, обязан иметь закрывающую пару.
* Незакрытый блок кода "поглощает" весь последующий текст документа, ломая рендеринг Markdown и скрывая заголовки от парсера. При обнаружении незакрытого блока бот немедленно блокирует слияние.

---

### 3.4. Система тегов внутри текста

Подход к тегированию основывается на жестком разделении: метаданные (в YAML) описывают *авторство*, а теги в теле документа — *статус конспекта*. 

Для предотвращения превращения базы в неконтролируемую свалку хештегов, **любые предметные и смысловые теги (например, `#кинематика`, `#интеграл`) в тексте строго запрещены.** Для поиска информации применяется встроенный полнотекстовый поиск.

В теле документа разрешены **исключительно 4 служебных тега** (проверяются по белому списку `ALLOWED_BODY_TAGS`):
* ✅ `#экзамен` / `#важно` — маркеры высокой важности, устанавливаются рядом с темами или определениями, необходимыми для сессии.
* ✅ `#дописать` / `#вопрос` — маркеры незавершенности (незаконченный вывод формулы, пропуск материала на лекции).

Обнаружение в тексте любого другого тега, начинающегося с `#` (и не находящегося внутри блока кода), вызывает ошибку: *"Запрещенный тег в тексте"*.

---

### 3.5. Текстовые акценты и Коллауты (Выноски)

Для выделения важной информации применяется синтаксис Callouts, который поддерживается как в Obsidian, так и нативно в GitHub.

* **Термины и определения:** Оформляются стандартной цитатой (`> `).
  ```markdown
  > **Механическая система** — совокупность материальных точек...
  ```
* **Законы, теоремы и правила:** Оформляются блоком `[!IMPORTANT]` (или `[!INFO]`).
  ```markdown
  > [!IMPORTANT]
  > Закон сохранения импульса
  > Суммарный импульс сохраняется во времени...
  ```
* **Примечания преподавателя:** Оформляются блоком `[!NOTE]`.
  ```markdown
  > [!NOTE]
  > Пояснение
  > Это работает только для замкнутых систем.
  ```

Для акцентирования внимания внутри абзацев используется:
* **Жирный шрифт** (`**текст**`) — для ключевых слов.
* **Подсветка маркером** (`==текст==`) — для фокуса на критичных деталях (в Obsidian отображается как желтый маркерный фон).

## ЧАСТЬ 4. Работа с медиафайлами и системные ограничения

Для сохранения работоспособности репозитория у всех участников и предотвращения неконтролируемого роста базы, проверяющий бот накладывает строгие ограничения на загружаемые файлы и пути к ним.

### 4.1. Абсолютные и локальные пути (КРИТИЧНАЯ ОШИБКА)

**Категорически запрещено использование локальных (абсолютных) путей к файлам!**  
При перетаскивании изображения в редактор из системных папок может сгенерироваться ссылка, привязанная к файловой системе конкретного компьютера. Такая ссылка будет работать только у вас, а у остальных пользователей отобразится ошибка рендеринга.

Бот парсит все стандартные ссылки `[]()` и вики-ссылки `[[]]` и немедленно отклоняет PR, если обнаруживает следующие паттерны:
* Протокол локального файла: `file://...`
* Буквы дисков Windows: `C:\...`, `D:/...`
* Системные директории UNIX/macOS: `/Users/...`, `/home/...`, `/root/...`, `/tmp/...`
* Сетевые пути: `\\...`

**Правильная настройка Obsidian:**  
Для автоматической генерации относительных путей необходимо настроить клиент Obsidian:
1. Перейдите в `Settings` (Настройки) -> `Files & Links` (Файлы и ссылки).
2. Параметр `Default location for new attachments` установите в значение **`In subfolder under current folder`**.
3. В появившемся поле `Subfolder name` укажите **`attachments`**.

После этой настройки все новые изображения будут автоматически складываться в правильную директорию с корректными относительными ссылками.

### 4.2. Ограничения файлов (Размер и расширения)

Система контроля версий (Git) не предназначена для хранения больших бинарных файлов. 

1. **Максимальный размер файла:** Лимит на размер ЛЮБОГО файла в репозитории составляет **10 МБ**. Файлы большего размера блокируются ботом.
2. **Белый список форматов:** К загрузке допускаются исключительно следующие форматы:
   * Документы: `.md`, `.pdf`
   * Изображения: `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`, `.svg`  
   Попытка загрузить файл с расширением, не входящим в данный список (например, `.txt`, `.docx`), вызовет ошибку валидации.
3. **Запрещенные медиаформаты:** Видеофайлы (`.mp4`, `.avi`), аудиозаписи лекций (`.mp3`, `.m4a`, `.wav`), архивы (`.zip`, `.rar`) и презентации (`.pptx`) загружать в репозиторий **запрещено**.
   * *Решение:* Загружайте тяжелые материалы на облачные хранилища (Яндекс.Диск, Google Drive, Облако Mail.ru) и вставляйте в markdown-файл обычную публичную ссылку для скачивания.
